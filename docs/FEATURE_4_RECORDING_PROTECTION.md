# 기능 4 — 중요 녹화 자동 삭제 방지

2026-10-20 구현. 기능 1~3 위에 보호 설정·조회와 보관 정책 연동을 추가했습니다. 기능 5~6은 아직 구현하지 않았습니다.

## 사용 방법

로그인 후 녹화 카드의 `중요 녹화로 보호`를 누르면 `보호 중 · 자동 삭제 제외`로 표시됩니다. `보호된 녹화만`을 선택하고 검색하면 날짜 조건과 함께 보호된 항목만 찾습니다. `전체 보기`는 날짜·보호 필터를 모두 초기화합니다. 전체 보관함의 확인된 보호 개수·용량도 표시합니다.

- 완성된 사건 MP4와 일반 녹화 MP4를 보호합니다. 병합 중인 `segment-*.mp4`는 원본 조각이 이동·소비되므로 보호 대상이 아닙니다. 카드에 완성 후 보호 가능으로 표시합니다.
- 보호는 원본 영상 내용·파일명·수정 시각을 바꾸지 않으며 앱·게이트웨이 재실행 뒤에도 유지합니다.
- 보호 설정 중에는 같은 파일의 중복 클릭을 막고, 서버 저장 결과 뒤 목록을 다시 읽습니다. 목록 갱신 때 재생 중인 녹화는 닫힙니다. 실패를 성공으로 먼저 표시하지 않습니다.
- `보호 해제`에는 확인창이 있습니다. 해제 자체는 원본을 삭제하지 않지만, **다음 보관 정리에서 바로 삭제될 수 있습니다.** 필요한 영상은 먼저 다운로드하세요.
- 이미 자동 정리가 끝난 파일에는 보호 성공을 반환하지 않습니다. 파일 없음으로 실패하며 삭제된 파일을 복원하는 기능은 아닙니다.
- 감시 수동 중지·화면 전용 휴식 중에도 Mac과 인증된 앱 세션이 깨어 있으면 설정을 변경할 수 있습니다. 시스템 잠자기 중 원격 접속은 제공하지 않습니다.

## 자동 정리와 공간 부족

Swift 보관 관리자는 기간 초과, 최대 보관 용량, 디스크 최소 여유 공간에 따른 자동 삭제에서 보호된 MP4를 건너뜁니다. 보호 파일 크기도 전체 보관량에 포함합니다. 보호 파일 때문에 용량/여유 공간 기준을 충족할 수 없다면 임의로 보호를 해제하거나 삭제하지 않습니다.

보관 점검의 공간 부족·메타데이터/잠금 오류는 진단 로그와 원격 상태판에 표시합니다. 상태판이 갱신되지 않으면 마지막 보고된 경고임을 구분합니다. 경고는 최근 보관 점검 결과이며 감시가 중지되어 점검하지 않는 동안에는 즉시 해소되지 않을 수 있습니다.

공간 확보가 불가능하면 새 녹화나 상태 파일 저장이 실패할 수 있습니다. 보호는 저장 용량을 늘리는 기능이 아닙니다. 외부 백업·공간 확보 또는 백업을 확인한 뒤 보호 해제가 필요합니다. 디스크 고장·직접 파일 삭제·로그아웃·재부팅 후 무인 시작 등 기존 보장 범위를 바꾸지는 않습니다. 보호는 별도 백업을 대신하지 않습니다.

## 영속 형식과 동시 실행

사용자 데이터의 `Recordings` 안에 다음 숨김 항목을 둡니다.

- `.recording-protection/<원본 MP4 이름>.keep`: 존재 자체가 보호 표시인 빈 일반 파일. 디렉터리는 0700, 새 표시 파일은 0600으로 만듭니다. JSON을 해석하지 않으므로 중간 쓰기나 형식 손상 때문에 보호가 해제되지 않습니다.
- `.recording-protection.lock`: 앱의 자동 삭제와 Go의 보호 변경이 함께 사용하는 영구 잠금 파일. macOS에서는 두 구현 모두 같은 파일에 OS `flock` 배타 잠금을 사용합니다.

보호 변경은 잠금 안에서 원본 존재 확인과 표시 생성/제거를 수행합니다. 자동 정리도 같은 잠금 안에서 보호 확인과 삭제를 수행합니다. 경합 시 자동 정리는 해당 회차를 보류하고, 보호 변경 요청은 최대 약 2초 기다렸다가 실패를 알립니다. 프로세스 종료 시 OS 잠금은 풀리며, 오래된 잠금 파일이 남아 있다는 사실만으로 잠긴 것은 아닙니다. **실행 중 잠금 파일을 삭제·교체하면 안 됩니다.**

보호 폴더를 읽지 못하거나 디렉터리 대신 파일/심볼릭 링크로 바뀌면 자동 정리는 안전하게 보류합니다. 개별 표시가 비정상 항목이어도 존재하면 해당 파일을 보호하고, 비정상 표시의 원격 해제는 거부합니다. 원격 목록에서 보호 정보를 읽지 못하면 상태 확인 불가·경고로 표시하며 보호 편집을 막습니다. 이런 경우 영상과 숨김 메타데이터를 먼저 백업하고 진단 로그로 원인을 확인하세요. 메타데이터 전체를 지우는 방식으로 해결하면 보호 정보가 사라질 수 있습니다.

파일을 수동으로 옮기거나 백업/복원할 때 MP4와 보호 폴더도 함께 보존해야 합니다. 다운로드한 MP4 한 개에는 이 로컬 보호 설정이 들어가지 않습니다. 표시 파일과 디렉터리 변경은 정전·물리 디스크 고장까지 보장하는 백업이나 트랜잭션 저장소가 아닙니다. 외부에서 원본/메타데이터를 직접 바꾸는 작업은 앱을 종료한 상태에서 진행하세요.

## 인증과 API

- `PUT /api/recordings/{id}/protection`, JSON `{"protected":true}` 또는 `{"protected":false}`. 상대 상태를 뒤집는 요청이 아니라 명시적 상태 저장이라 같은 요청의 반복이 안전합니다.
- 기존 로그인 세션, 정확한 Origin, 세션 CSRF 토큰을 모두 요구합니다. 본문 최대 1024바이트, 필수 boolean, 알 수 없는 필드·추가 JSON을 거부합니다. 성공은 저장한 `protected` 상태를 반환합니다.
- `/api/recordings`에 파일별 `protected`, `protectionSupported`, `protectionAvailable`을 추가했습니다. 목록 페이지에는 전체 보관함 기준 `protectedCount`, `protectedBytes`, 필요 시 `protectionWarning`을 담습니다. 상태 미확인 항목은 확인된 개수·용량에 포함하지 않습니다.
- 목록의 `protected=1`은 확인된 보호 파일만 반환하며 기존 날짜·페이지 조건과 함께 쓸 수 있습니다.
- `/api/status`의 `monitoring.retentionWarning`은 앱의 최근 보관 경고입니다. 이전 버전 상태 파일에 이 필드가 없어도 읽을 수 있습니다.

재생·썸네일·다운로드 인증을 유지합니다. 직접 삭제 API는 추가하지 않았습니다. 로그아웃은 이미 승인된 저장 요청을 취소하거나 보호 설정을 되돌리는 명령이 아니며, 늦게 온 응답이 비공개 화면을 다시 띄우지는 못하게 했습니다.

## 실행한 검사와 미검증 범위

- Windows Go: 총 28개 중 25개 통과, 3개 건너뜀. 신규 보호 영속성·재호출·필터·원본 불변·손상 메타데이터·OS 잠금 경합/해제, 인증/Origin/CSRF/엄격한 본문·만료 세션·404를 검사했습니다. Windows에서는 개발 검사에 맞는 OS 파일 잠금 구현을 사용하고, 제품의 macOS 빌드는 Swift와 같은 `flock`을 사용합니다.
- 건너뛴 3개: 기존 원본 심볼릭 링크 검사, 신규 보호 메타데이터/표시 심볼릭 링크 검사(Windows 생성 권한 없음), 실제 FFmpeg 디스크립터 검사(macOS/Linux 전용).
- Node 화면 제어 검사 13개 통과. 보호 요청의 CSRF, 중복 방지·재조회, 보호만 검색, 해제 취소, 저장 실패, 로그아웃 뒤 늦은 응답, 상태 미확인 편집 차단·공간 경고를 포함합니다. 미국 뉴욕 시간대로도 실행해 기존 DST 검색을 유지했습니다. 실제 브라우저가 아닌 DOM 대역 검사입니다.
- Swift 테스트 4개를 추가했습니다: 기간/용량/여유 공간 압력에서도 보호와 재시작 유지, 해제 뒤 정리 재개, 메타데이터 오류/잠금 경합 시 보류·복구, 심볼릭 링크 거부와 잠금 권한. 기존 보관 테스트는 숨김 잠금 파일을 녹화 항목으로 세지 않도록 조정했고, 상태판 테스트에 보관 경고 저장을 추가했습니다.
- `go vet ./...`, Darwin/amd64 교차 빌드와 공백 오류 검사도 실행했습니다.

**Windows에는 Swift/macOS 프레임워크가 없어 Swift 테스트와 Mac의 앱↔게이트웨이 실제 동시 실행은 아직 검증 전입니다.** 교차 빌드는 Mac에서 실행했다는 뜻이 아닙니다.

## Mac 인수 테스트

1. 최신 ZIP을 새 폴더에 풀고 `Build MacMonitor.command`를 더블클릭합니다. 새 `RecordingProtectionTests`와 Go 보호 테스트가 통과하는지 확인합니다. 테스트는 임시 폴더의 가짜 영상만 정리하므로 실제 보관 기준을 낮춰 시험할 필요가 없습니다.
2. 실제 중요한 영상은 먼저 별도 다운로드/백업합니다. HTTPS 녹화 목록에서 테스트용 완성 사건을 보호하고 표시·전체 보호 용량을 확인합니다. 보호만 보기와 날짜 검색을 함께 확인합니다.
3. 감시를 멈췄다 켜고, 앱을 종료 후 다시 인증해 실행합니다. 보호가 유지되고 재생·썸네일·다운로드가 가능한지 확인합니다.
4. 테스트 영상의 보호 해제 확인창에서 취소해 상태가 유지되는지 확인합니다. 삭제되어도 괜찮은 영상만 해제하고, 이후 정상 보관 정책 도달 시 정리되는지 관찰합니다. 기존 중요한 원본을 대상으로 보관 한도를 급격히 줄이지 마세요.
5. 비로그인·로그아웃 상태에서 보호 변경이 거부되는지 확인합니다. 감시 중지·화면 전용 휴식에서도 보호 조회/설정이 가능한지 확인합니다.
6. 테스트용 사건을 여러 번 보호/해제하거나 두 인증 브라우저에서 새로고침하며 감시 FPS·재생·로그를 확인합니다. 실제 공간 부족을 만들거나 운영 중 메타데이터·잠금 파일을 임의로 삭제하지 않습니다. 보관 경합/오류·공간 압력은 우선 임시 폴더의 XCTest로 검증합니다.
