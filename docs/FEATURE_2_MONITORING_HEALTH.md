# 기능 2 — 실제 감시 상태와 프레임 정지 복구

2026-10-20 구현. 웹 서버 접속 성공과 실제 카메라 프레임 수신을 분리해서 표시합니다. 기능 1의 감시 독립 원격 녹화 접근을 유지하며 기능 3~6은 아직 구현하지 않았습니다.

## 원격 상태판

로그인 후 실시간·녹화 탭 위에 다음 항목을 약 5초 주기로 표시합니다.

- 감시 상태: 시작 중, 새 프레임 수신, 첫 영상 대기, 프레임 정지, 복구 중, 수동 중지, 예약 휴식, 시스템 잠자기, 오류.
- 실제 카메라 수신 FPS와 마지막 프레임 시각. 인코더가 반복 전송한 프레임 수가 아닌 캡처 콜백 도착 횟수를 측정합니다.
- 마지막 움직임 감지 시각, 최근 사건 MP4 완성 시각, 디스크 가용 용량.
- 이번 앱 실행 중 프레임 정지를 감지해 복구를 요청한 횟수. 복구 성공 횟수와는 다릅니다.

움직임이 없을 때 새 사건 파일이 없는 것은 정상입니다. 상태판은 이를 녹화 장애라고 표시하지 않습니다. 마지막 완성 시각은 보관 정책으로 그 파일이 삭제되더라도 과거 완료 기록으로 남을 수 있습니다. 앱 재실행 시에는 기존 `motion-*.mp4` 파일에서 최근 완료 시각을 읽습니다.

캡처 콜백이 계속 도착하는 것은 최종 원격 영상 재생이나 모든 인코딩 결과까지 검증했다는 뜻은 아닙니다. 웹 서버 연결 상태와 실제 프레임 도착 상태를 별도로 보여주며, 실제 Safari 재생·녹화 파일 재생은 Mac 인수 테스트로 확인합니다.

## 정지 감지와 복구

- 카메라가 실행 상태로 전환된 뒤 첫 프레임은 15초까지 기다립니다.
- 프레임을 받기 시작한 뒤에는 새 프레임이 10초 동안 없으면 복구를 요청합니다. 감지 주기가 2초이므로 최대 약 2초가 추가될 수 있습니다.
- 화면 내용이 같은지는 판단하지 않습니다. 조용한 방에서도 새 프레임이 도착하면 정상입니다.
- 카메라 시작 준비·권한 확인·수동 중지·예약 휴식·시스템 잠자기·복구 대기 동안에는 정지 감지를 하지 않습니다.
- 벽시계 변경의 영향을 받지 않도록 경과 시간은 시스템 uptime으로 계산합니다. 새 실행마다 감지 상태를 초기화하고 같은 실행에서는 한 번만 장애를 보고합니다.
- 기존 감시 코디네이터의 카메라·인코더 정리와 2/5/15초 복구, 안정 동작 후 예산 초기화를 사용합니다. 예산을 소진하면 감시 오류로 표시하고 사용자의 재시작을 기다립니다. 원격 녹화 웹 서버는 중단하지 않습니다.

## 상태 전달

앱은 사용자 전용 `Runtime/monitoring-status.json`을 약 2초 주기로 원자적으로 교체합니다. 파일 권한은 0600이며 비밀번호·인증서·영상 데이터는 넣지 않습니다. 프레임 콜백은 메모리만 갱신하고 디스크 쓰기는 별도 큐에서 합니다.

게이트웨이는 인증된 `/api/status` 응답의 `monitoring`에 이 상태를 담습니다. 기존 설정도 `gateway.json` 옆 `Runtime/monitoring-status.json`을 기본으로 읽습니다. 필요하면 절대 경로의 `monitoringStatusFile`을 지정할 수 있습니다.

15초 넘게 갱신이 없거나 파일이 없고 손상된 경우 정상으로 표시하지 않습니다. 오래된 상태는 `상태 갱신 지연`, 읽을 수 없는 상태는 `상태 확인 불가`로 표시하며 녹화 목록·재생 기능은 계속 제공합니다. 상태 쓰기 실패가 프레임 정지 감지 자체를 막지는 않습니다.

## 검증

- Go 테스트 16개 및 `go vet ./...` 통과. 상태 파일 검사는 정상·첫 영상 유예·정지·중지·휴식·복구·오래된 갱신·미래 시각·알 수 없는 형식·손상·과대 파일과 이전 설정의 기본 경로를 포함합니다.
- Darwin/amd64 게이트웨이 교차 빌드 성공.
- Node 화면 제어 테스트 5개 통과. 기능 1의 전환·로그아웃 검사와 함께 실제 수신/휴식/정지/오래된 상태의 표시를 확인했습니다. DOM 대역 검사이며 Safari 렌더링 검증은 아닙니다.
- Swift 테스트 4개 추가: 첫 프레임 유예와 실행당 한 번만 복구, 도착 프레임 FPS·정지 경계, 중지/재개 초기화, 실제 상태 파일의 휴식/실행/종료·사건 시각·파일 권한.

Windows에는 Swift/macOS 프레임워크가 없어 Swift 테스트와 실제 카메라 재시작은 아직 실행하지 못했습니다. Mac의 빌드 파일이 일반 XCTest와 Thread Sanitizer를 실행합니다.

## Mac 인수 테스트

1. 최신 ZIP을 새 폴더에 풀어 빌드하고 HTTPS 설정 후 로그인합니다. 감시를 켜기 전에는 중지 상태와 FPS `—`가 보여야 합니다.
2. 감시 시작 후 프레임 시각과 실제 FPS가 갱신되는지 확인합니다. 고요한 화면에서 1분 이상 기다려도 정지 감지 횟수가 증가하지 않아야 합니다.
3. 움직임을 만들고 사건 파일이 완성된 뒤 마지막 움직임·녹화 시각을 확인합니다. 움직임 없는 구간에서 새 녹화가 없다는 이유로 오류를 내면 안 됩니다.
4. 수동 중지와 화면 전용 휴식에서 FPS `—`, 중지/휴식 상태를 확인하고 20초 이상 기다려 자동 감시 재시작이 없는지 확인합니다. 과거 녹화는 계속 재생되어야 합니다.
5. 외장 카메라가 있다면 촬영 중 연결을 끊어 오류·복구·프레임 갱신 재개를 확인합니다. 내장 카메라를 임의로 비활성화하는 명령은 사용하지 않습니다. 통지 없이 프레임만 멈추는 경계는 추가한 Swift 단위 테스트로 확인합니다.
6. 메뉴의 진단 로그 폴더를 연 뒤 상위 `Runtime`의 상태 파일 갱신을 관찰합니다. 앱의 프레임 시각과 원격 표시가 일치하는지 확인합니다. stale 판정은 Go 회귀 검사로 검증했으며 운영 중 상태 파일을 수동 변조할 필요는 없습니다.
