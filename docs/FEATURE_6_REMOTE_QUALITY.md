# 기능 6 — 원격 화질 프로필과 자동 조절

2026-10-20 구현. 원격 화면에 `자동 조절`, `원본 스트림`, `표준`, `절약`을 추가했습니다. 선택은 브라우저별로 기억하며 저장소 사용이 제한된 브라우저에서는 현재 페이지 동안만 유지합니다. 다른 시청자의 선택이나 로컬 녹화 설정을 바꾸지 않습니다.

## 프로필과 녹화 분리

| 선택 | 원격 영상 | 인코딩 목표 | 원본 녹화 |
|---|---|---|---|
| 원본 스트림 | 현재 앱의 원본 스트림 (기본 720p/15fps) | 앱의 비트레이트 설정 | 변경 없음 |
| 표준 | 854×480, 10fps | 약 700kbps | 변경 없음 |
| 절약 | 640×360, 8fps | 약 300kbps | 변경 없음 |
| 자동 조절 | 표준으로 시작, 상태에 따라 한 단계씩 변경 | 선택된 프로필에 따름 | 변경 없음 |

목표 비트레이트는 실제 네트워크 총사용량의 보장이 아닙니다. 코덱 버퍼와 장면에 따라 달라지고 RTP/암호화/통신 헤더 등 추가 비용이 있습니다. 원본 프로필도 카메라의 최대 해상도라는 뜻이 아니라 **앱이 현재 캡처·인코딩한 영상**입니다. 이 앱의 캡처는 여전히 720p/15fps로 설정되며 4K 카메라 원본 캡처를 새로 추가하지 않았습니다.

로컬 녹화와 원본 RTSP tee는 기존 하나의 H.264 인코딩을 그대로 유지합니다. MediaMTX의 `live-balanced`/`live-low` 경로를 요청한 동안에만 원본 `live`를 읽어 별도로 작게 인코딩합니다. 같은 프로필의 여러 시청자는 그 프로필의 인코더를 공유하며 서로 다른 프로필은 각각 인코더를 사용합니다. 두 축소 프로필을 동시에 보면 최대 두 개의 추가 인코더가 동작할 수 있습니다.

원본 보기에는 추가 영상 인코더가 필요하지 않습니다. 표준·절약에는 VideoToolbox H.264와 필요 시 소프트웨어 대체를 사용하므로 iMac의 CPU/GPU·발열·하드웨어 인코더 수용량 검증이 필요합니다. 입력·필터 스레드를 제한했지만 자원 사용이 0이 되거나 저사양 기기에서 끊기지 않는다는 보장은 아닙니다.

시청자가 없어지면 MediaMTX의 약 5초 유예 후 해당 프로필 생성 명령을 닫습니다. 휴대폰 브라우저를 백그라운드로 보내거나 녹화 탭으로 이동하면 실시간 연결을 정리하며, 다시 표시할 때 인증 확인 후 연결합니다. 화면을 다시 표시하는 것은 휴대폰/PC의 브라우저 동작이며 iMac 디스플레이를 깨우는 명령은 사용하지 않습니다.

프로필 전환은 WebRTC 재연결이므로 잠깐 영상이 끊길 수 있습니다. 이 동안 카메라와 원본 녹화를 재시작하지 않습니다. 기록에 영향을 주지 않도록 원격 인코더 장애를 감시 파이프라인의 복구 요청으로 연결하지 않았습니다. 추가 인코딩으로 인한 실제 시스템 자원 경합까지 제거했다는 뜻은 아닙니다.

## 자동 조절과 통계

- 약 2초마다 브라우저 WebRTC 수신 통계의 차이를 계산해 실제 kbps/FPS, 패킷 손실, 선택된 연결의 RTT를 표시합니다. 미지원 통계는 `—`로 표시하고 프레임 진행도 별도로 봅니다.
- 손실 8% 초과, RTT 700ms 초과, 드롭 20% 초과, 프로필 목표의 절반 미만 FPS 또는 영상 정지를 나쁜 표본으로 봅니다. 나쁜 표본 2회 이상과 최소 약 10초의 프로필 유지 조건에서 한 단계 낮춥니다.
- 좋은 표본 30회와 약 60초 안정 조건 뒤 한 단계 높여 시험합니다. 저화질이 잘 나온다는 사실만으로 상위 화질 대역폭을 보장하지 않으므로 재차 나빠지면 다시 내립니다. 미지원/불충분 통계로 상향하지 않습니다.
- 수동 선택은 자동으로 다른 화질로 바꾸지 않습니다. 원본이 계속 끊기면 직접 표준/절약 또는 자동 모드를 선택하세요.
- 일시정지·자동 재생 차단은 정상 재생 대기와 구분합니다. 첫 영상은 약 15초, 재생 중 프레임 진행 중단은 약 12초 뒤 연결 복구를 요청합니다. 연결 절차 자체는 25초 제한이며 주기적 인증 확인에도 제한 시간을 둡니다.
- 자동 모드의 연결 실패는 가능한 경우 한 단계 낮추며, 2/4/8/8초 대기하는 최대 4회 재시도 뒤 멈추고 사용자 재연결을 기다립니다. 연속 수신이 확인된 후에는 복구 예산을 초기화합니다. 서버 측 프로필 시작 실패는 기존 MediaMTX on-demand 시작 제한도 따릅니다.

## 인증·통신 경로

커스텀 수신기는 같은 HTTPS 출처의 인증된 `/live/{프로필}/whep`에 SDP를 보내고, 같은 출처의 허용된 세션 주소만 사용합니다. 초기 ICE 후보를 모아서 한 번에 전달하는 방식이며 TURN/STUN 서버는 추가하지 않았습니다. 기존 공인 주소/DDNS·수동 포트포워딩과 고정 ICE UDP/TCP 8189의 직접 연결 조건을 유지합니다. CGNAT이나 접근 불가 회선을 압축으로 해결할 수는 없습니다.

화질 선택·재연결·로그아웃 시 이전 peer와 세션을 정리합니다. 늦게 도착한 연결 응답은 폐기하고, 새 세션이 만들어진 경우 삭제를 요청합니다. 플레이어를 별도 탭으로 열어도 약 10초마다 인증을 다시 확인해 만료 시 연결을 닫습니다. 이미 승인된 미디어 연결에 대해 즉각적인 서버 측 강제 철회 API를 새로 추가한 것은 아니며, 브라우저 확인 주기/연결 종료까지의 지연이 있을 수 있습니다.

프로필의 입력·출력 RTSP는 모두 127.0.0.1 내부 경로입니다. 추가 외부 포트나 공유기 자동 설정·중계 서버를 만들지 않습니다. 클라이언트가 보내는 화질 이름을 임의 실행 명령으로 조립하지 않고, 미리 정의된 세 경로만 사용합니다.

사용 중인 고정 버전의 [MediaMTX 설정](https://raw.githubusercontent.com/bluenviron/mediamtx/v1.21.1/mediamtx.yml)의 on-demand 경로와 [WHEP 서버 구현](https://raw.githubusercontent.com/bluenviron/mediamtx/v1.21.1/internal/servers/webrtc/http_server.go)의 SDP·세션 주소 형식을 참고했습니다. 참고 자료 확인은 실제 Mac 연결 시험을 대신하지 않습니다.

## 실행한 검사와 Mac 검증

- Node 화면·수신기 검사 총 26개 통과: 기존 1~4번 회귀 검사와 수동 화질/탭 전환, 통계 차분, 자동 하향·상향·미지원 통계, 수동 모드 유지, SDP 요청·세션 삭제·외부 주소 차단, 닫힌 후 응답, 재시도 상한, 만료 인증, 일시정지/정지/첫 프레임 시간 초과, 백그라운드 정리를 확인했습니다. DST 검색을 위해 뉴욕 시간대로도 실행했습니다. RTC/DOM 대역 검사라 실제 미디어를 전송하지는 않았습니다.
- Go 검사 총 29개 중 26개 통과, 기존 3개 건너뜀. 새 정적 플레이어 파일, 화질별 인증·SDP/세션 Location 프록시·삭제와 외부 주소 거부를 포함합니다. `go vet ./...` 및 Darwin/amd64 게이트웨이 교차 빌드도 실행했습니다.
- 기능 5의 Swift 테스트 4개 외에 기능 6 테스트 3개를 추가했습니다: on-demand 프로필/loopback/녹화 출력 분리, 실행 파일 경로 인용·개행 거부, 생성한 전체 설정의 고정 MediaMTX 바이너리 검사. 마지막 테스트는 `vendor/mediamtx/mediamtx`가 있을 때 실행합니다. 더블클릭 빌드 순서에서는 먼저 고정 바이너리를 준비합니다.

**Windows에서는 Swift 빌드·AppKit 미리보기·고정 MediaMTX 설정 검사·VideoToolbox 추가 인코딩·실제 WebRTC/Safari를 실행하지 못했습니다.** 모든 기능의 소스 구현과 실행 가능한 검사는 완료했지만 Mac 실기 인수는 남아 있습니다.

1. 최신 ZIP을 새 폴더에 풀어 더블클릭 빌드합니다. 새 Swift 테스트와 `testGeneratedConfigurationWithPinnedMediaMTXValidatorWhenAvailable`의 성공을 확인합니다. 실패하면 로그를 보존하고 무시해서 실행하지 않습니다.
2. 감시 시작 후 HTTPS로 접속해 원본·표준·절약을 각각 선택합니다. 표준은 480p/10fps, 절약은 360p/8fps 근처로 수신되는지 확인합니다. 실제 FPS는 카메라 상태판의 15fps와 플레이어 안 통계가 서로 다른 지표입니다.
3. 움직임을 만들면서 화질을 여러 번 바꾼 뒤, 원본 MP4를 내려받아 연결 전후 영상·시간 연속성·기존 녹화 화질이 유지되는지 확인합니다.
4. 휴대폰 데이터망에서 자동 모드를 켜고 수신 상태 변화에 따른 하향·안정 뒤 상향을 관찰합니다. 전환 시 재연결 지연을 기록합니다. 수동 절약 모드에서는 자동 상향이 없어야 합니다. 테스트를 위해 운영 공유기 설정을 임의 변경하지 않습니다.
5. 녹화 탭 이동·브라우저 백그라운드·로그아웃 후 iMac의 추가 FFmpeg 인코더가 유예 뒤 종료되는지 확인합니다. 원본 캡처/녹화 인코더는 감시 중 계속 남아 있어야 합니다. 다시 표시하면 재연결·인증 검사가 되어야 합니다.
6. 두 시청자에서 서로 다른 축소 프로필을 선택하고 CPU·메모리·발열·실제 캡처 FPS와 녹화 정상 여부를 관찰합니다. 문제가 있으면 한 시청자를 원본 또는 절약으로 바꾸고 로그를 보존합니다. 실제 4K나 특정 회선에서의 무끊김을 사전 보장하지 않습니다.
