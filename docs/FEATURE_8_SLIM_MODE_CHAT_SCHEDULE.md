# 기능 8 — 슬림 모드, 텔레그램 명령, 원격 녹화

2026-11-08 설계·구현. 사용자의 요청은 세 가지였습니다. (1) Mac이 평소에는 잠들어 있다가 10분마다 스스로 깨어나 원격 실시간 요청이 있는지 확인하고, 있으면 깬 상태로 영상을 보내다가 끝나면 다시 잠든다. (2) 요청은 텔레그램 봇 같은 채팅으로 보낸다. (3) 움직임 감지 녹화 대신 시간표에 따른 녹화가 필요하고, 용량을 제한한다.

같은 날 저녁, 첫 Mac 빌드 뒤 사용자가 요일·시간표 예약 녹화를 없애고 가장 단순한 형태로 가자고 결정했습니다. 남는 기능은 (a) 원격 접속 실시간 시청, (b) 원격에서 시간을 골라 시작하면 접속이 끊어져도 이어지는 녹화, (c) 텔레그램 확인과 슬림 모드 깨우기입니다. §5는 그 결정에 맞춰 원격 녹화로 바꿔 적었습니다.

이 문서는 설계 검토 결과와 구현 내용을 함께 적습니다. Swift 부분은 이 작업 환경(Windows)에서 컴파일되지 않았고, 전원 동작은 대상 iMac에서만 판정할 수 있습니다. 확정된 것과 확인이 필요한 것을 §7에서 구분합니다.

## 3. 슬림 모드 — 잠들어 있다가 주기적으로 깨어나기

### 3.1 지금 동작과 바뀌는 점

지금은 `원격 시청 대기`가 켜져 있으면 앱이 `PreventUserIdleSystemSleep` assertion을 계속 잡아 Mac이 잠들지 않습니다. 화면만 꺼지고 시스템은 깨어 있어 접속이 바로 됩니다(기능 7). 전력은 계속 씁니다.

슬림 모드를 켜면 다음과 같이 바뀝니다.

1. 시청자도 없고 원격 녹화도 없으면 assertion을 놓습니다. 거기에 더해 깨어난 뒤 90초가 지났고, 잠에서 깬 뒤라면 깬 뒤로 키보드·마우스 입력이 없을 때, 앱을 실행한 뒤 아직 잠든 적이 없다면 입력이 5분 이상 없을 때 `pmset sleepnow`로 바로 잠듭니다. Energy Saver의 잠자기 시간이 "안 함"이어도, 화면 공유(`sharingd`)가 유휴 잠자기를 막고 있어도 잠듭니다. (2026-11-09 변경, §3.5)
2. 잠들기 직전(`NSWorkspace.willSleepNotification`)에 `sudo -n /usr/bin/pmset schedule wake "MM/dd/yy HH:mm:ss" MacMonitor`로 다음 깨우기를 예약합니다. 시각은 `지금 + 확인 간격`(기본 10분)입니다. 원격 녹화는 끝날 때까지 Mac을 깨어 있게 하므로 따로 깨우기가 필요 없습니다.
3. 깨어나면(`didWakeNotification`) 90초 동안 `PreventSystemSleep` assertion을 잡습니다. 이 종류는 화면을 켜지 않는 dark wake도 열어 두므로, 예약 깨우기가 몇 초 만에 다시 잠드는 일을 막습니다. 그동안 Wi‑Fi가 붙고 게이트웨이가 다시 뜨고 텔레그램을 확인합니다. 요청이 있으면 임대 파일이 바뀌고, 기존 경로대로 카메라가 켜지며 시청이 끝난 뒤 60초가 지나야 다시 잠들 수 있습니다. 요청이 없으면 1번으로 돌아갑니다.
4. 예약한 깨우기 시각 전후 2분 안에 깨어났고 입력이 없으면, 기존 매일 예약 깨우기와 같은 방식으로 `pmset displaysleepnow`를 한 번 보냅니다.

깨어 있는 시간은 한 주기(기본 10분)에 약 1분 30초입니다.

### 3.2 왜 이렇게 했는가

- **잠자기 유도 명령을 넣은 이유.** Energy Saver 유휴 잠자기만 믿으면 깨어난 뒤 다시 잠드는 시점이 설정에 따라 10~30분 뒤가 되거나 "안 함"이면 영원히 깨어 있습니다. 사용자가 말한 "없으면 다시 슬림 모드"는 능동적으로 돌아가는 동작이므로 `pmset sleepnow`를 씁니다. 입력 무응답 조건은 `DisplaySleepController`가 화면을 끌 때 쓰는 입력 확인(`CGEventSource.secondsSinceLastEventType`, 모든 입력 종류를 합친 `kCGAnyInputEventType`)과 같은 방식입니다. Mac 앞에 사람이 있으면 잠들지 않습니다. 잠들기 전의 입력은 깬 뒤의 "사람이 있음"으로 보지 않습니다(§3.5).
- **sudoers 규칙을 쓰는 이유.** `pmset schedule`은 root 권한이 필요합니다. 기존 매일 예약은 `with administrator privileges`로 저장할 때 한 번 비밀번호를 받지만, 10분마다 비밀번호를 받을 수는 없습니다. `scripts/enable-slim-mode.sh`가 현재 사용자에게 `pmset schedule wake *`와 `pmset schedule cancel wake *`만 비밀번호 없이 허용하는 규칙을 `/etc/sudoers.d/macmonitor`에 넣습니다. 문법 오류가 있으면 Mac 전체의 `sudo`가 망가지므로 임시 파일을 `visudo -cf`로 검사한 뒤에만 설치합니다. 규칙이 없으면 앱은 슬림 모드를 켜도 지금처럼 깨어 있는 대기를 유지하고 메뉴에 그 이유를 표시합니다.
- **깨우기를 잠들기 직전에 예약하는 이유.** 앱이 잠자기를 유도한 경우와 다른 원인(Energy Saver, 사용자)으로 잠드는 경우를 한 곳에서 처리합니다. 다만 매일 예약 휴식(`시스템 잠자기` 모드)의 휴식 시간에 잠드는 경우에는 10분 뒤 깨우기를 예약하지 않습니다. 그 시간의 깨우기는 기존 `pmset repeat` 예약이 맡습니다.
- **예약 결과를 다시 읽는 이유.** 예약 뒤 `pmset -g sched`에 `MacMonitor` 항목이 있는지 읽어 없으면 메뉴에 오류를 표시합니다. 터미널 없이 규칙 누락을 알 수 있는 유일한 방법입니다.
- **잠들기 전에 먼저 시험하는 이유.** 앱 시작과 설정 변경 때 하루 뒤 깨우기를 실제로 예약하고 목록에서 확인한 뒤 취소합니다(`PowerCommandRunner.proveWakeScheduling`). sudo 규칙, 날짜 형식, 취소까지 한 번에 확인되며, 하나라도 실패하면 슬림 모드는 assertion을 놓지 않고 메뉴에 실패한 단계를 표시합니다. 잠들기 직전에 처음 실패를 알면 Mac은 이미 잠들어 누가 와서 깨울 때까지 멈춥니다. 이 시험은 명령과 형식이 받아들여지는 것까지만 증명하고, 실제로 그 시각에 깨어나는지는 Mac 확인 항목입니다.
- **깨어남 알림이 오지 않는 경우.** 예약 깨우기가 화면을 켜지 않는 "dark wake"로 처리되면 `didWakeNotification`이 오지 않을 수 있습니다. 10초 점검 타이머가 벽시계 경과와 `systemUptime` 경과를 비교해 30초 넘게 차이가 나면 잠자기가 있었다고 보고 같은 90초 확인 창을 엽니다.

### 3.3 구조

```text
willSleep ──▶ PowerCommandRunner.scheduleWake(now+간격)
                 sudo -n pmset schedule wake "MM/dd/yy HH:mm:ss" MacMonitor
                 pmset -g sched 로 확인
(잠자기)
didWake / 시간 간격 감지 ──▶ lastWakeUptime = 지금
   │  90초 확인 창: PreventSystemSleep assertion 유지, 게이트웨이 재시작, 텔레그램 확인
   ├─ 임대 갱신됨 ──▶ 기존 경로: CaptureModePolicy → live / 녹화 → 시청 종료 후 60초 유지
   └─ 요청 없음, 깬 뒤 입력 없음(또는 실행 뒤 입력 5분 무응답) ──▶ pmset sleepnow ──▶ willSleep (처음으로)
```

판단은 `SlimModePolicy.decide`(순수 함수)에 모았습니다. 입력은 슬림 모드 켜짐, 예약 가능 여부, 시청·녹화 요구, 깨어난 뒤 경과 시간, 마지막 요구 종료 뒤 경과 시간, 마지막 입력 뒤 경과 시간, 이번 실행에서 잠들었다 깬 적이 있는지이고 출력은 `holdAwake`(assertion 유지) / `allowIdleSleep`(assertion 해제) / `sleepNow`(잠자기 유도) 세 가지입니다. `AppDelegate.updateRemotePower`가 이 결정을 기존 `standing` 조건과 합칩니다.

### 3.4 경계와 실패 처리

- 슬림 모드가 꺼져 있으면 모든 동작이 이전과 같습니다. 규칙이 없거나 `sudo -n`이 실패하면 `holdAwake`로 고정됩니다.
- 잠자기 유도는 깨어난 뒤 90초 안에는 하지 않고, 깬 뒤 입력이 있으면 하지 않습니다. 시청·녹화 중에는 절대 하지 않습니다.
- 결정의 이유를 10초마다 상태 파일(`slimDetail`)에 쓰고, 바뀔 때마다 Console에 `MacMonitor slim:`으로 남깁니다. 웹 상태 보드의 `슬림 모드` 칸과 텔레그램 `상태` 답장의 `슬림: …`이 같은 문장을 보입니다. 잠자기 요청, 깨우기 예약, 잠들기, 깨어남도 같은 접두어로 기록합니다.
- 앱 종료 시 자기가 넣은 깨우기 예약을 취소합니다. 제거 스크립트는 sudoers 규칙과 `MacMonitor`가 소유한 깨우기 예약을 지웁니다.
- 수동 잠자기(Apple 메뉴)도 슬림 모드에서는 10분 뒤 깨어납니다. Mac을 완전히 재워 두려면 슬림 모드를 끕니다.
- 매일 예약 휴식의 `시스템 유지 · 화면만 끄기` 시간에는 잠자기를 유도하지 않습니다. 그 모드는 사용자가 "시스템을 켜 둔다"고 정한 것이고 `pmset sleepnow`는 그 assertion을 무시하기 때문입니다. 휴식이 끝나면 다시 슬림 모드 규칙을 따릅니다.
- 화면: 예약 깨우기가 화면을 켜는지는 Mac에서만 알 수 있습니다. 켠다면 10분마다 잠깐 켜지는 현상이 생기며, 이는 요구사항 7과 충돌하는 이 모드의 비용입니다. 확인 간격을 늘려 줄일 수 있지만 없앨 수는 없습니다. §7의 첫 확인 항목입니다.

### 3.5 2026-11-09 조사 — 화면이 꺼져도 잠들지 않고, 재운 뒤 답이 없던 이유

사용자가 보고한 현상은 둘입니다. (a) 슬림 모드를 켜고 가만히 두면 화면만 꺼지고 10분이 지나도 잠들지 않는다. (b) Apple 메뉴로 재운 뒤 5분 넘게 지나 텔레그램 `상태`를 보내도 답이 없다(그 전 22:05·22:15의 `상태` 답장은 왔고 `슬림 모드`라고 적혀 있었다). Windows에서 코드와 테스트만으로 조사했고, Mac에서 재현하지 못했습니다. 아래 "확인"은 코드 읽기와 테스트로 확인한 것이고 Mac 동작은 §7의 확인 항목입니다.

경쟁 가설과 판정:

| 가설 | 판정 | 근거 |
|---|---|---|
| `sharingd`가 잠자기를 막는다 | 부분 기각 | `pmset sleepnow`는 사용자 요청 잠자기라 유휴 assertion을 무시하므로 `sleepNow` 경로에는 영향이 없다. 그러나 `allowIdleSleep` 경로(입력이 최근이라 assertion만 놓는 경우)는 Energy Saver 유휴 잠자기에 맡기는데, `sharingd`가 그것을 막으므로 그 경로로는 영원히 잠들지 않는다. |
| 화면이 꺼지면 입력 없음으로 친다 | 기각 | 화면 끄기는 Energy Saver의 디스플레이 시간이고, 판단은 `CGEventSource`의 마지막 입력 시각만 본다. 둘은 무관하다. |
| 잠들기 전의 입력이 깬 뒤에도 "사람이 있음"으로 센다 | 확인 (원인 1) | `decide`는 `secondsSinceInput < 600`이면 `allowIdleSleep`을 돌려 주고, 잠든 동안 이 값은 거의 멈춘다. Apple 메뉴를 클릭한 그 입력이 깬 뒤 다시 10분 동안 Mac을 깨워 두고, 그 사이 다음 판단은 위의 `sharingd` 경로로 빠진다. 재운 뒤 깨어나서 다시 잠들지 않는 주기가 생긴다. |

변경:

1. `SlimModePolicy`에 `wokeFromSleep` 입력을 더해, 잠들었다 깬 뒤에는 깬 뒤의 입력만 "사람이 있음"으로 봅니다. 잠들기 전 입력은 무시합니다. 앱 실행 뒤 아직 잠든 적이 없으면 전처럼 입력 시각을 보되, 기준을 10분에서 5분으로 줄였습니다. Energy Saver 유휴 잠자기는 `sharingd` 때문에 믿을 수 없으므로 이 기준이 유일한 존재 판단입니다.
2. 확인 창을 60초에서 90초로 늘리고, 그 동안 `PreventSystemSleep` assertion을 잡아 dark wake도 열어 둡니다(`IdleSleepPreventer(kind: .preventSystemSleep)`). 이 assertion은 잠들기 직전(`willSleep`)에 미리 잡습니다. dark wake가 몇 초 만에 끝나면 10초 점검 타이머가 깨어남을 알아채기 전일 수 있어, 깨어난 뒤에 잡으면 늦기 때문입니다. 사용자 요청 잠자기(`pmset sleepnow`, Apple 메뉴)는 이 assertion을 무시하므로 잠드는 데는 영향이 없고, 깬 뒤 90초가 지나면 놓습니다. Wi‑Fi 재접속 시간을 고려했습니다. 깨우는 키 입력은 앱이 깨어남을 기록하기 직전 시각으로 찍힐 수 있어 5초 안의 입력은 깬 뒤의 입력으로 봅니다.
3. 텔레그램 시청 창은 웹 시청자가 임대를 갱신하다 90초 동안 사라지면, 또는 3분 동안 아무도 링크를 열지 않으면 10분을 기다리지 않고 끝내고 그 이유를 답장합니다(`Bot.ViewerSeen` ← `server.LastViewerDemand`). 그래서 `카메라` 시험이 Mac을 10분 넘게 깨워 두지 않습니다.
4. 결정의 이유를 문장으로 만들어(`SlimModePolicy.explain`) 상태 파일 `slimDetail`, 웹 `슬림 모드` 칸, 텔레그램 `상태` 답장의 `슬림: …`에 보이고, 바뀔 때마다 Console에 남깁니다. 잠자기 요청·깨우기 예약·잠들기·깨어남도 `MacMonitor slim:` 접두어로 기록합니다.
5. `매일 예약 휴식 · 화면만 끄기`의 유휴 잠자기 방지 assertion은 휴식 시간에만 잡습니다. 전에는 그 모드를 켜 두면 하루 종일 잡고 있었습니다.
6. `enable-slim-mode.sh`는 `sudo`로 실행되면(`SUDO_USER`가 있거나 root이면) 설치하지 않고 로그인 사용자로 실행하라고 안내합니다(회귀 검사 추가). 설정 파일을 읽지 못해 기본값으로 뜨면 메뉴에 `설정 파일 오류 — …`를 보이고, 설정 창에서 관리자 비밀번호를 취소하면 "취소했습니다"를 보이고 이전 값을 다시 읽습니다.
7. 입력 확인은 `kCGAnyInputEventType`(모든 입력 종류의 합산 카운터)을 먼저 쓰고, 그 값이 열거형으로 바뀌지 않으면 기존 종류별 목록으로 돌아갑니다.

Mac에서 보아야 할 것(§7의 12~14번): 재운 뒤 다음 깨어남에 `상태` 답장이 오는지, 그 답장의 `슬림: …`이 무엇을 말하는지, Console의 `MacMonitor slim:` 줄이 "깨어난 뒤 입력 없음 · 잠자기 요청" → "requesting sleep" → "wake scheduled" → "system is going to sleep" 순서로 남는지. 현상 (b)의 두 후보는 `pmset -g log | grep -iE "Wake|Sleep"`와 `pmset -g sched`로 가립니다. 이 둘은 이제 텔레그램 `진단`으로 받습니다(§3.6).

### 3.7 2026-11-10 진단 결과: dark wake에서는 카메라가 켜지지 않음

보고: 슬림 모드를 끈 채 Mac을 강제로 재우고 23:09에 `상태`·`카메라`·`진단`을 보냈다. 답은 23:39에 왔고 웹은 `카메라 켜는 중`에서 멈췄으며 Mac은 곧 다시 잠들었다.

- 23:39:20 깨어남은 `DarkWake … [CDNPB] : due to RTC XHC1/Maintenance`다. macOS의 정기 점검이 깨운 것이어서 답이 30분 늦었다. 카메라가 정상이던 22:45:12의 깨어남은 `Wake … [CDNVA]`(V 영상, A 소리)다.

- 앱 로그에서 dark wake(22:40:00, 23:39:19)는 `sleep detected from the clock gap`이 `woke up`보다 먼저 찍혔고, 완전한 깨어남(22:45:12)은 `woke up`이 먼저 찍혔다. 즉 `didWakeNotification`은 완전한 깨어남에만 온다.
- 같은 카메라 서비스 프로세스와 같은 앱 프로세스가 22:45 이후에는 프레임 1955개를 받았다. 그래서 §3.6의 두 번째·세 번째 후보(카메라 서비스 멈춤, 캡처 세션 고장)는 기각했다.
- 미확인: 진단이 카메라 시작 5초 뒤에 찍혀, 23:39:25의 시작이 프레임 0개로 끝났는지와 직후의 `Sleep` 줄은 담기지 않았다.

수정(사용자 결정, 2026-11-11): 깨어남을 알림 없이 시계 차이로만 알아챈 경우를 dark wake로 보고(`darkWakeSuspected`), 그 상태에서 캡처 요청이 오면 `IOPMAssertionDeclareUserActivity`로 완전한 깨어남을 한 번 요청한다(`FullWakeRequester`). 이때 화면이 켜지므로 1초 뒤 `pmset displaysleepnow`로 다시 끈다(깬 뒤 입력이 있으면 끄지 않음). 요구사항 7(원격 접속이 화면을 켜지 않음)은 이 경우에만 양보한다. 화면만 꺼지고 시스템이 깨어 있는 평소의 접속은 이 경로를 타지 않는다. 슬림 모드가 꺼져 있으면 깨우는 예약이 없어, 재운 Mac은 macOS가 스스로 깰 때까지 명령을 받지 못하는 점은 그대로다.

Windows에서는 Swift를 컴파일하지 못해 이 수정은 Mac에서 처음 빌드되고 실행된다(§7의 17~19번).

1. `scripts/configure-telegram.sh <봇 토큰>`을 실행하고, 안내에 따라 휴대폰에서 봇에게 아무 말이나 보냅니다. 스크립트가 그 채팅 번호를 찾아 보여 주고, 확인하면 `~/Library/Application Support/MacMonitor/telegram.json`(0600)에 토큰·채팅 번호·시청 유지 시간(기본 10분)을 저장합니다.
2. 게이트웨이가 이 파일을 10초마다 확인해 생기거나 바뀌면 봇을 (다시) 시작합니다. 앱 재시작은 필요 없습니다.
3. 봇은 `getUpdates`를 25초 long polling으로 기다립니다. 허용된 채팅 번호의 메시지만 처리합니다.
   - `카메라`, `보여줘`, `켜`, `영상`, `live`, `cam` → 시청 창을 열고 임대 파일을 5초마다 갱신합니다. 답장: `카메라를 켭니다 · https://주소 · 10분 동안 유지`. 이어서 상태 파일을 최대 60초 지켜보고 `카메라가 켜졌습니다 (N초)` 또는 실패 원인을 답장합니다. 웹 시청자가 임대를 갱신하다 90초 동안 사라지거나 3분 동안 아무도 링크를 열지 않으면 10분 전에 창을 끝내고 그 이유를 답장합니다(2026-11-09, §3.5). 시청자 기록은 게이트웨이 메모리에만 있어, 게이트웨이가 다시 뜨면(잠자기마다) 복원된 창은 시청자가 없던 것으로 보고 시작 3분이 지났으면 끝냅니다. 보고 있었다면 다시 `카메라`를 보냅니다.
   - `그만`, `꺼`, `중지`, `stop` → 시청 창을 닫습니다. 웹 시청자가 보고 있으면 그 임대는 그대로 유지됩니다.
   - `상태`, `status` → 상태 파일 요약을 답장합니다.
   - `진단`, `diag` → 잠자기·깨어남 기록, 깨우기 예약, 잠을 막는 요청, 카메라 장치·서비스, 앱 카메라·게이트웨이·앱 로그 요약을 답장합니다(2026-11-09, §3.6). 잠든 동안 보낸 것도 답합니다.
   - 그 외 → 명령 목록을 답장합니다.
4. 30분 넘게 지난 `카메라` 요청은 무시하고 다시 보내 달라고 답장합니다. Mac이 꺼져 있다가 몇 시간 뒤 켜졌을 때 옛 요청으로 카메라가 켜지는 것을 막습니다.
5. 처리한 메시지 번호(offset)와 시청 창 시작·종료 시각을 `Runtime/telegram-state.json`에 저장합니다. 잠자기마다 게이트웨이가 새로 뜨므로, 저장하지 않으면 깨어날 때마다 같은 명령을 다시 처리합니다.

### 4.2 왜 게이트웨이에 두는가

- 임대 파일을 쓰는 코드(`health.RecordLiveDemand`), 공개 주소, 상태 파일 경로가 모두 게이트웨이에 있습니다. 봇이 쓰는 것은 그 셋뿐입니다.
- Go는 이 환경에서 컴파일·테스트할 수 있습니다. 가짜 텔레그램 서버(`httptest`)로 명령 처리, 채팅 번호 거부, 오래된 요청 거부, 재시작 뒤 상태 복원을 실행해 확인합니다. Swift에 두면 전부 미검증이 됩니다.
- 앱은 바뀌지 않습니다. 텔레그램에서 온 요청과 웹에서 온 요청을 구분하지 않고 같은 임대로 봅니다.

### 4.3 경계와 보안

- 봇 토큰은 `telegram.json`에 0600으로 저장하고 로그에 쓰지 않습니다. 토큰이 유출되면 봇을 다시 만들어야 합니다.
- 허용 채팅 하나만 명령할 수 있습니다. 다른 채팅의 메시지는 번호만 로그에 남기고 답장하지 않습니다. 설치 스크립트는 이 로그가 아니라 API 응답으로 번호를 찾습니다.
- 새 외부 통신은 `api.telegram.org`로 나가는 HTTPS 하나입니다. 들어오는 포트는 열지 않습니다.
- 같은 토큰으로 두 프로세스가 `getUpdates`를 부르면 텔레그램이 409를 돌려줍니다. 봇은 30초 쉬고 다시 시도하며 로그에 남깁니다.
- 게이트웨이의 기존 HTTP 클라이언트는 2초 제한이라 long polling에 쓸 수 없습니다. 봇은 40초 제한의 자기 클라이언트를 씁니다.
- 텔레그램 명령도 웹 비밀번호와 같은 수준의 권한입니다. 사용자의 텔레그램 계정에 접근할 수 있는 사람은 카메라를 켤 수 있습니다. 표시등은 그대로 켜집니다.

## 5. 원격 녹화 — 웹에서 시간을 골라 시작하는 연속 저장

2026-11-08 저녁에 요일·시간표 예약 녹화를 이 기능으로 대체했습니다. 제거한 예약 녹화의 기록은 §5.4에 있습니다.

### 5.1 동작

- 웹 실시간 화면에 `원격 녹화` 시간 선택(1·2·3·4·6·8·12·24시간)과 `녹화 시작` 버튼이 있습니다. 누르면 게이트웨이가 `Runtime/recording-demand.json`에 `{"schemaVersion":1,"until":"<끝 시각, RFC 3339 UTC>","hours":N,"requestedAt":…}`을 원자적으로 씁니다. `녹화 중지`는 이 파일을 지웁니다.
- 앱은 2초마다 이 파일을 읽어(`RecordingDemandMonitor`) 끝 시각이 지나지 않았으면 `timed` 모드로 카메라를 켭니다. 시청 임대와 달리 갱신이 없으므로 접속을 끊어도, 휴대폰을 잠가도 그 시각까지 계속 녹화합니다. 끝 시각은 벽시계 기준입니다. 사용자가 "4시간"을 요청한 것이므로 깨어 있던 시간이 아니라 실제 시각으로 끝내는 것이 맞습니다.
- 녹화 중에는 `remote-YYYYMMDDTHHMMSS.mp4`를 10분마다 `Spool`에 쓰고, 닫힌 파일을 `Recordings`로 옮겨 웹 목록에 바로 보입니다. 움직임 감지는 하지 않습니다. 시청자는 같은 영상을 봅니다.
- 상태: 메뉴는 `원격 녹화 중 — 카메라 · HH:mm까지`, 웹 상태판의 `녹화` 칸은 `켜짐 · 원격`, 웹의 녹화 줄은 `원격 녹화 중 · HH:MM까지 · 남은 N시간 M분`입니다. 다른 기기에서 접속해도 같은 파일을 읽으므로 같은 표시와 `녹화 중지` 버튼이 보입니다. Mac 메뉴에도 `원격 녹화 중지`가 있습니다.
- 우선순위: 원격 녹화 > 수동 움직임 녹화 > 시청자 요청 > 꺼짐. 원격 시청처럼 메뉴의 `원격 시청 대기`가 꺼져 있으면 원격 녹화도 시작되지 않습니다. 그 메뉴가 "원격이 카메라를 쓸 수 있는가"의 주인 스위치이기 때문입니다. 매일 예약 휴식 시간에는 지금처럼 모든 녹화를 쉽니다.
- 보관: 기존 보관 관리자가 `Recordings`의 모든 MP4를 기간·용량·디스크 여유 기준으로 정리합니다. 1,200kbps에서 시간당 약 0.5GB, 24시간은 약 13GB로 기본 20GB 안에 듭니다.
- 슬림 모드: 원격 녹화 중에는 시청자처럼 Mac을 깨어 있게 하고, 끝난 뒤 1분이 지나면 다시 잠들 수 있습니다. 잠든 Mac에는 웹으로 접속할 수 없으므로 텔레그램 `카메라`로 먼저 깨운 뒤 링크에서 녹화를 시작합니다.
- 시작 때 영상이 잠시 끊깁니다. 실시간 전용과 녹화는 인코더 출력이 달라 캡처를 다시 시작하기 때문이며, 플레이어가 스스로 다시 연결합니다. 웹 안내문에 적어 두었습니다.

### 5.3 왜 보관 관리자를 그대로 쓰는가

용량 제한(`maximumBytes`), 보관 기간, 최소 여유, 보호 파일 제외, 공유 잠금이 모두 `RecordingRetentionManager.enforceRetention`에 있습니다. 연속 녹화용 클래스를 따로 만들면 이 규칙을 복제해야 합니다. 대신 `keepEverySegment` 한 플래그로 "어떤 세그먼트를 남길지"만 바꿨습니다. 움직임 병합(`mergeFinalizedEvents`)은 `segment-` 접두어만 다루므로 `remote-` 파일에는 손대지 않습니다.

열려 있는 파일을 옮기는 경우: 승격 시점은 파일 이름의 시작 시각 + 길이 + 10초입니다. FFmpeg가 늦게 닫아 아직 쓰는 중이라도 APFS에서 열린 파일의 이름 변경은 쓰기를 끊지 않으며, 파일은 새 위치에서 완성됩니다. 그 몇 초 동안 웹 목록에는 재생되지 않는 파일로 보일 수 있습니다.

### 5.4 기록 — 제거한 예약 녹화

요일(월~일)·시작·종료 시각·파일 길이(5·10·30분)를 설정 창에 두고 그 창 안에서 `schedule-*.mp4`를 연속 저장하는 기능이었습니다. `RecordingSchedule.swift`와 테스트 8개, 설정 창 5줄, 슬림 모드의 "창 시작 1분 전 깨우기"를 함께 제거했습니다. 첫 Mac 빌드(19:05)에서 컴파일과 테스트는 통과했지만 실제 창 녹화는 Mac에서 확인되지 않은 채 제거되었습니다. 사용자의 결정은 "가장 단순하게: 원격 시청, 원격에서 시작해 끊어져도 이어지는 녹화(시간만 설정), 텔레그램 확인과 깨우기"입니다. 되돌리려면 커밋 `abb0f29` 시점의 파일을 참고합니다.

## 6. 설정과 스크립트

- 설정 창: `슬림 모드` 체크와 확인 간격(5·10·15·30·60분). 원격 녹화는 설정 창에 항목이 없고 웹에서 시작합니다. 저장하면 앱이 10초 안에 적용합니다.
- `scripts/enable-slim-mode.sh`: sudoers 규칙 설치(관리자 비밀번호 한 번). 설치 뒤 `sudo -n -l`로 규칙이 적용됐는지 스스로 확인합니다.
- `scripts/configure-telegram.sh <토큰>`: 봇 확인(`getMe`), 채팅 번호 찾기, `telegram.json` 저장.
- `scripts/uninstall.sh`: sudoers 규칙과 `MacMonitor` 깨우기 예약을 제거 항목에 추가했습니다. 관리자 비밀번호가 필요하므로 매일 예약 해제와 같은 단계에서 따로 확인받습니다.
- `scripts/diagnose.sh`: `telegram.json` 검증, sudoers 규칙 유무, Energy Saver 잠자기가 "안 함"인지 경고.
- 게이트웨이 `check-config`: `telegram.json`이 있으면 함께 검증합니다.

## 7. Mac에서 확인해야 하는 것 (미확인)

구현했지만 이 환경에서 실행하지 못한 항목입니다. 위에서부터 중요한 순서입니다.

1. **예약 깨우기가 화면을 켜는지.** 켜면 10분마다 잠깐 점등합니다. `pmset -g log | grep -i wake`로 `DarkWake`인지 `Wake`인지 확인합니다.
2. `pmset schedule wake "MM/dd/yy HH:mm:ss" MacMonitor`의 날짜 형식이 받아들여지고 그 시각에 실제로 깨어나는지. 형식과 sudo 규칙은 앱의 시험 예약이 확인하므로, 실패하면 메뉴에 `슬림 모드 대기 — 깨우기 예약 확인 실패`가 보입니다. 실제로 깨어나는지는 기다려서 봅니다.
3. `pmset sleepnow`가 일반 사용자 권한으로 되는지. 안 되면 sudoers 규칙에 추가해야 합니다.
4. 예약 깨우기에서 `didWakeNotification`이 오는지. 오지 않아도 시간 간격 감지로 확인 창이 열리는지 Console 로그로 봅니다.
5. 깨어난 뒤 90초 안에 네트워크가 올라오고 게이트웨이가 텔레그램 메시지를 받는지(Wi‑Fi는 더 느릴 수 있음).
6. LaunchAgent로 실행된 앱에서 `sudo -n`이 규칙을 읽는지.
7. `IOPMSchedulePowerEvent`를 root 없이 부를 수 있는지. 된다면 sudoers 없이 구현할 수 있어 규칙을 없앱니다.
8. 실제 텔레그램 API: long polling, 답장, 409 처리.
9. 원격 녹화: 웹을 닫은 뒤에도 10분 세그먼트가 제때 닫히고 `Recordings`로 옮겨진 뒤 Safari에서 재생되는지. 시각이 되거나 `녹화 중지`를 누르면 마지막 짧은 파일도 옮겨지는지. 시작 때 끊긴 플레이어가 스스로 다시 연결되는지.
10. 원격 녹화로 바뀐 Swift 소스의 컴파일과 새 `RecordingDemandTests` 3개. 첫 Mac 빌드(19:05)는 예약 녹화 버전이었습니다.
11. 설정 창 높이는 움직임 감지 줄을 빼고 720pt입니다. 저장 버튼이 보이는지 확인합니다.
12. (2026-11-09) Apple 메뉴로 재운 뒤 다음 확인 간격에 깨어나 텔레그램 `상태`에 답하는지. 답장의 `슬림: …` 문장과 Console의 `MacMonitor slim:` 줄을 기록합니다. 답이 없으면 `pmset -g log | grep -iE "Wake|Sleep" | tail -n 20`에서 `DarkWake` 뒤 몇 초 만에 `Sleep`이 오는지, `pmset -g sched`에 `MacMonitor` 항목이 있는지 봅니다.
13. (2026-11-09) 깨어난 뒤 Mac을 건드리지 않으면 약 90초 뒤 다시 잠드는지(`깨어난 뒤 입력 없음 · 잠자기 요청` → `requesting sleep`). 깬 뒤 키보드를 한 번 누르면 5분 동안 잠들지 않는지.
