# 기능 8 — 슬림 모드, 텔레그램 명령, 용량 제한 예약 녹화

2026-11-08 설계·구현. 사용자의 요청은 세 가지였습니다. (1) Mac이 평소에는 잠들어 있다가 10분마다 스스로 깨어나 원격 실시간 요청이 있는지 확인하고, 있으면 깬 상태로 영상을 보내다가 끝나면 다시 잠든다. (2) 요청은 텔레그램 봇 같은 채팅으로 보낸다. (3) 움직임 감지 녹화 대신 시간표에 따른 녹화가 필요하고, 용량을 제한한다.

이 문서는 설계 검토 결과와 구현 내용을 함께 적습니다. Swift 부분은 이 작업 환경(Windows)에서 컴파일되지 않았고, 전원 동작은 대상 iMac에서만 판정할 수 있습니다. 확정된 것과 확인이 필요한 것을 §7에서 구분합니다.

## 1. 검토 결과 요약

| No. | 요청 | 설계 결정 | 판단 |
|---|---|---|---|
| 1 | 10분마다 깨어나 요청 확인 | `pmset schedule wake`로 다음 깨우기를 예약하고, 깨어난 뒤 60초 동안 요청을 기다렸다가 없으면 `pmset sleepnow`로 다시 잠듭니다. 관리자 비밀번호 없이 예약하도록 sudoers 규칙 한 줄을 설치 스크립트로 넣습니다. | 구현. 깨우기 예약의 날짜 형식, 화면 점등 여부, 잠자기 명령 권한은 **Mac에서 확인** |
| 2 | 채팅으로 "카메라 보여줘" | Go 게이트웨이 안의 텔레그램 봇이 허용된 채팅 하나의 명령만 받아, 기존 시청 임대 파일(`live-demand.json`)을 10분 동안 갱신하고 웹 주소를 답장합니다. 앱은 바뀌지 않은 경로로 카메라를 켭니다. | 구현. 실제 텔레그램 API 연동은 **Mac에서 확인** |
| 3 | 스케줄 녹화, 용량 제한 | 요일·시간 창에 10분 단위 MP4를 연속 저장합니다. 용량 제한은 이미 있는 `최대 녹화 용량 (GB)`과 오래된 것부터 삭제하는 보관 관리자를 그대로 씁니다. | 구현 |
| 4 | 움직임 감지 녹화 제거 | 이번에는 제거하지 않고 메뉴에 그대로 둡니다. 새 기능은 어느 것도 움직임 녹화를 거치지 않습니다. | 보류. 제거는 Mac에서 예약 녹화를 확인한 뒤 |

용량 제한의 뜻: 기본 1,200kbps로 녹화하면 시간당 약 0.5GB입니다. 기본값 20GB면 약 40시간 분량을 보관하고, 넘치면 보호하지 않은 파일 중 가장 오래된 것부터 지웁니다. 보관 기간(기본 14일)과 최소 디스크 여유(기본 5GB)도 그대로 적용됩니다.

## 2. 검토 범위와 판단 기준

읽은 코드: `AppDelegate.swift`의 상태 전이, `CaptureModePolicy`, `LiveDemandMonitor`, `IdleSleepPreventer`, `DisplaySleepController`, `PowerScheduleSettings`, `DailySleepSchedule`, `LocalMonitoringPipeline`, `FFmpegPipeline`, `RecordingRetentionManager`, `MonitoringHealthReporter`, 게이트웨이의 `server.go`·`config.go`·`health/*.go`·`recordings/store.go`, 웹 `app.js`, 스크립트 `uninstall.sh`·`diagnose.sh`·`configure-gateway.sh`.

판단 기준:

- 요구사항 7(원격 접속이 iMac 화면을 켜거나 잠금을 풀지 않음)과 10(카메라 표시등을 숨기지 않음)을 유지합니다.
- 앱과 게이트웨이는 지금처럼 파일로만 통신하고, 앱에 새 포트를 열지 않습니다.
- 기존 시청 임대·모드 결정·보관 관리자를 재사용하고, 새 상태 값은 게이트웨이와 웹의 계약(상태 파일 허용 값, 파일 이름 규칙)까지 함께 바꿉니다.
- 이 환경에서 실행할 수 있는 것(Go·Node·스크립트)은 실행해 확인하고, Swift와 전원 동작은 미확인으로 남깁니다.

## 3. 슬림 모드 — 잠들어 있다가 주기적으로 깨어나기

### 3.1 지금 동작과 바뀌는 점

지금은 `원격 시청 대기`가 켜져 있으면 앱이 `PreventUserIdleSystemSleep` assertion을 계속 잡아 Mac이 잠들지 않습니다. 화면만 꺼지고 시스템은 깨어 있어 접속이 바로 됩니다(기능 7). 전력은 계속 씁니다.

슬림 모드를 켜면 다음과 같이 바뀝니다.

1. 시청자도 없고 녹화 창도 아니면 assertion을 놓습니다. 거기에 더해 깨어난 뒤 60초가 지났고 키보드·마우스 입력이 10분 이상 없으면 `pmset sleepnow`로 바로 잠듭니다. Energy Saver의 잠자기 시간이 "안 함"이어도 잠듭니다.
2. 잠들기 직전(`NSWorkspace.willSleepNotification`)에 `sudo -n /usr/bin/pmset schedule wake "MM/dd/yy HH:mm:ss" MacMonitor`로 다음 깨우기를 예약합니다. 시각은 `지금 + 확인 간격`(기본 10분)과 `다음 예약 녹화 시작 1분 전` 중 이른 것입니다.
3. 깨어나면(`didWakeNotification`) 60초 동안 assertion을 잡습니다. 그동안 게이트웨이가 다시 뜨고 텔레그램을 확인합니다. 요청이 있으면 임대 파일이 바뀌고, 기존 경로대로 카메라가 켜지며 시청이 끝난 뒤 60초가 지나야 다시 잠들 수 있습니다. 요청이 없으면 1번으로 돌아갑니다.
4. 예약한 깨우기 시각 전후 2분 안에 깨어났고 입력이 없으면, 기존 매일 예약 깨우기와 같은 방식으로 `pmset displaysleepnow`를 한 번 보냅니다.

깨어 있는 시간은 한 주기(10분)에 약 1분입니다.

### 3.2 왜 이렇게 했는가

- **잠자기 유도 명령을 넣은 이유.** Energy Saver 유휴 잠자기만 믿으면 깨어난 뒤 다시 잠드는 시점이 설정에 따라 10~30분 뒤가 되거나 "안 함"이면 영원히 깨어 있습니다. 사용자가 말한 "없으면 다시 슬림 모드"는 능동적으로 돌아가는 동작이므로 `pmset sleepnow`를 씁니다. 입력 10분 무응답 조건은 `DisplaySleepController`가 화면을 끌 때 쓰는 입력 확인(`CGEventSource.secondsSinceLastEventType`)과 같은 방식입니다. Mac 앞에 사람이 있으면 잠들지 않습니다.
- **sudoers 규칙을 쓰는 이유.** `pmset schedule`은 root 권한이 필요합니다. 기존 매일 예약은 `with administrator privileges`로 저장할 때 한 번 비밀번호를 받지만, 10분마다 비밀번호를 받을 수는 없습니다. `scripts/enable-slim-mode.sh`가 현재 사용자에게 `pmset schedule wake *`와 `pmset schedule cancel wake *`만 비밀번호 없이 허용하는 규칙을 `/etc/sudoers.d/macmonitor`에 넣습니다. 문법 오류가 있으면 Mac 전체의 `sudo`가 망가지므로 임시 파일을 `visudo -cf`로 검사한 뒤에만 설치합니다. 규칙이 없으면 앱은 슬림 모드를 켜도 지금처럼 깨어 있는 대기를 유지하고 메뉴에 그 이유를 표시합니다.
- **깨우기를 잠들기 직전에 예약하는 이유.** 앱이 잠자기를 유도한 경우와 다른 원인(Energy Saver, 사용자)으로 잠드는 경우를 한 곳에서 처리합니다. 다만 매일 예약 휴식(`시스템 잠자기` 모드)의 휴식 시간에 잠드는 경우에는 10분 뒤 깨우기를 예약하지 않습니다. 그 시간의 깨우기는 기존 `pmset repeat` 예약이 맡습니다.
- **예약 결과를 다시 읽는 이유.** 예약 뒤 `pmset -g sched`에 `MacMonitor` 항목이 있는지 읽어 없으면 메뉴에 오류를 표시합니다. 터미널 없이 규칙 누락을 알 수 있는 유일한 방법입니다.
- **잠들기 전에 먼저 시험하는 이유.** 앱 시작과 설정 변경 때 하루 뒤 깨우기를 실제로 예약하고 목록에서 확인한 뒤 취소합니다(`PowerCommandRunner.proveWakeScheduling`). sudo 규칙, 날짜 형식, 취소까지 한 번에 확인되며, 하나라도 실패하면 슬림 모드는 assertion을 놓지 않고 메뉴에 실패한 단계를 표시합니다. 잠들기 직전에 처음 실패를 알면 Mac은 이미 잠들어 누가 와서 깨울 때까지 멈춥니다. 이 시험은 명령과 형식이 받아들여지는 것까지만 증명하고, 실제로 그 시각에 깨어나는지는 Mac 확인 항목입니다.
- **깨어남 알림이 오지 않는 경우.** 예약 깨우기가 화면을 켜지 않는 "dark wake"로 처리되면 `didWakeNotification`이 오지 않을 수 있습니다. 10초 점검 타이머가 벽시계 경과와 `systemUptime` 경과를 비교해 30초 넘게 차이가 나면 잠자기가 있었다고 보고 같은 60초 확인 창을 엽니다.

### 3.3 구조

```text
willSleep ──▶ PowerCommandRunner.scheduleWake(min(now+간격, 다음 녹화 창-1분))
                 sudo -n pmset schedule wake "MM/dd/yy HH:mm:ss" MacMonitor
                 pmset -g sched 로 확인
(잠자기)
didWake / 시간 간격 감지 ──▶ lastWakeUptime = 지금
   │  60초 확인 창: assertion 유지, 게이트웨이 재시작, 텔레그램 확인
   ├─ 임대 갱신됨 ──▶ 기존 경로: CaptureModePolicy → live / 녹화 → 시청 종료 후 60초 유지
   └─ 요청 없음, 입력 10분 무응답 ──▶ pmset sleepnow ──▶ willSleep (처음으로)
```

판단은 `SlimModePolicy.decide`(순수 함수)에 모았습니다. 입력은 슬림 모드 켜짐, 예약 가능 여부, 시청·녹화 요구, 깨어난 뒤 경과 시간, 마지막 요구 종료 뒤 경과 시간, 마지막 입력 뒤 경과 시간이고 출력은 `holdAwake`(assertion 유지) / `allowIdleSleep`(assertion 해제) / `sleepNow`(잠자기 유도) 세 가지입니다. `AppDelegate.updateRemotePower`가 이 결정을 기존 `standing` 조건과 합칩니다.

### 3.4 경계와 실패 처리

- 슬림 모드가 꺼져 있으면 모든 동작이 이전과 같습니다. 규칙이 없거나 `sudo -n`이 실패하면 `holdAwake`로 고정됩니다.
- 잠자기 유도는 깨어난 뒤 60초 안에는 하지 않고, 입력이 있으면 하지 않습니다. 시청·녹화 중에는 절대 하지 않습니다.
- 앱 종료 시 자기가 넣은 깨우기 예약을 취소합니다. 제거 스크립트는 sudoers 규칙과 `MacMonitor`가 소유한 깨우기 예약을 지웁니다.
- 수동 잠자기(Apple 메뉴)도 슬림 모드에서는 10분 뒤 깨어납니다. Mac을 완전히 재워 두려면 슬림 모드를 끕니다.
- 매일 예약 휴식의 `시스템 유지 · 화면만 끄기` 시간에는 잠자기를 유도하지 않습니다. 그 모드는 사용자가 "시스템을 켜 둔다"고 정한 것이고 `pmset sleepnow`는 그 assertion을 무시하기 때문입니다. 휴식이 끝나면 다시 슬림 모드 규칙을 따릅니다.
- 화면: 예약 깨우기가 화면을 켜는지는 Mac에서만 알 수 있습니다. 켠다면 10분마다 잠깐 켜지는 현상이 생기며, 이는 요구사항 7과 충돌하는 이 모드의 비용입니다. 확인 간격을 늘려 줄일 수 있지만 없앨 수는 없습니다. §7의 첫 확인 항목입니다.

## 4. 텔레그램 명령 채널

### 4.1 동작

1. `scripts/configure-telegram.sh <봇 토큰>`을 실행하고, 안내에 따라 휴대폰에서 봇에게 아무 말이나 보냅니다. 스크립트가 그 채팅 번호를 찾아 보여 주고, 확인하면 `~/Library/Application Support/MacMonitor/telegram.json`(0600)에 토큰·채팅 번호·시청 유지 시간(기본 10분)을 저장합니다.
2. 게이트웨이가 이 파일을 10초마다 확인해 생기거나 바뀌면 봇을 (다시) 시작합니다. 앱 재시작은 필요 없습니다.
3. 봇은 `getUpdates`를 25초 long polling으로 기다립니다. 허용된 채팅 번호의 메시지만 처리합니다.
   - `카메라`, `보여줘`, `켜`, `영상`, `live`, `cam` → 시청 창을 열고 임대 파일을 5초마다 갱신합니다. 답장: `카메라를 켭니다 · https://주소 · 10분 동안 유지`. 이어서 상태 파일을 최대 60초 지켜보고 `카메라가 켜졌습니다 (N초)` 또는 실패 원인을 답장합니다.
   - `그만`, `꺼`, `중지`, `stop` → 시청 창을 닫습니다. 웹 시청자가 보고 있으면 그 임대는 그대로 유지됩니다.
   - `상태`, `status` → 상태 파일 요약을 답장합니다.
   - 그 외 → 명령 목록을 답장합니다.
4. 30분 넘게 지난 `카메라` 요청은 무시하고 다시 보내 달라고 답장합니다. Mac이 꺼져 있다가 몇 시간 뒤 켜졌을 때 옛 요청으로 카메라가 켜지는 것을 막습니다.
5. 처리한 메시지 번호(offset)와 시청 창 종료 시각을 `Runtime/telegram-state.json`에 저장합니다. 잠자기마다 게이트웨이가 새로 뜨므로, 저장하지 않으면 깨어날 때마다 같은 명령을 다시 처리합니다.

### 4.2 왜 게이트웨이에 두는가

- 임대 파일을 쓰는 코드(`health.RecordLiveDemand`), 공개 주소, 상태 파일 경로가 모두 게이트웨이에 있습니다. 봇이 쓰는 것은 그 셋뿐입니다.
- Go는 이 환경에서 컴파일·테스트할 수 있습니다. 가짜 텔레그램 서버(`httptest`)로 명령 처리, 채팅 번호 거부, 오래된 요청 거부, 재시작 뒤 상태 복원을 실행해 확인합니다. Swift에 두면 전부 미검증이 됩니다.
- 앱은 바뀌지 않습니다. 텔레그램에서 온 요청과 웹에서 온 요청을 구분하지 않고 같은 임대로 봅니다.

### 4.3 경계와 보안

- 봇 토큰은 `telegram.json`에 0600으로 저장하고 로그에 쓰지 않습니다. 토큰이 유출되면 봇을 다시 만들어야 합니다.
- 허용 채팅 하나만 명령할 수 있습니다. 다른 채팅의 메시지는 번호만 로그에 남기고 답장하지 않습니다. 설치 스크립트는 이 로그가 아니라 API 응답으로 번호를 찾습니다.
- 새 외부 통신은 `api.telegram.org`로 나가는 HTTPS 하나입니다. 들어오는 포트는 열지 않습니다.
- 같은 토큰으로 두 프로세스가 `getUpdates`를 부르면 텔레그램이 409를 돌려줍니다. 봇은 30초 쉬고 다시 시도하며 로그에 남깁니다.
- 게이트웨이의 기존 HTTP 클라이언트는 2초 제한이라 long polling에 쓸 수 없습니다. 봇은 40초 제한의 자기 클라이언트를 씁니다.
- 텔레그램 명령도 웹 비밀번호와 같은 수준의 권한입니다. 사용자의 텔레그램 계정에 접근할 수 있는 사람은 카메라를 켤 수 있습니다. 표시등은 그대로 켜집니다.

## 5. 예약 녹화 — 요일·시간 창에 연속 저장

### 5.1 동작

- 설정에 `예약 녹화 사용`, 요일(월~일), 시작·종료 시각, 파일 길이(5·10·30분)를 추가했습니다. 기본은 꺼짐, 월~금 09:00~18:00, 10분입니다. 종료가 시작보다 이르면 자정을 넘는 창입니다.
- 창 안에서는 카메라를 켜고 `schedule-YYYYMMDDTHHMMSS.mp4` 파일을 10분마다 `Spool`에 쓴 뒤, 닫힌 파일을 `Recordings`로 옮깁니다. 움직임 감지는 하지 않습니다. 시청자는 같은 영상을 봅니다.
- 보관: 기존 보관 관리자가 `Recordings`의 모든 MP4를 기간·용량·디스크 여유 기준으로 정리하므로 새 파일도 같은 규칙을 받습니다. 보호한 파일은 지우지 않습니다.
- 모드 우선순위: 예약 녹화 창 > 수동 움직임 녹화 > 시청자 요청 > 꺼짐. 매일 예약 휴식 시간에는 지금처럼 모든 녹화를 쉽니다. 두 시간표가 겹치면 휴식이 이깁니다.
- 슬림 모드와의 관계: 녹화 창은 시청자처럼 Mac을 깨어 있게 합니다. 잠들기 직전 예약하는 깨우기 시각이 창 시작 1분 전보다 늦으면 창 시작 1분 전으로 당깁니다.

### 5.2 구현 위치

| 바뀐 곳 | 내용 |
|---|---|
| `MonitoringModels.swift` | `CaptureMode.scheduled` 추가, `CaptureModePolicy.desiredMode`에 `scheduledRecording` 입력 추가, 상태 문구 `예약 녹화 중 — 카메라` |
| `RecordingSchedule.swift` (신규) | 요일·시간 창 판정 `isActive(at:)`, 다음 시작 `nextStart(after:)`, 검증 |
| `AppConfiguration.swift` | `recordingSchedule`, `slimMode` 필드. 예전 설정 파일은 둘 다 꺼짐으로 읽음 |
| `FFmpegPipelineConfiguration` | 세그먼트 파일 접두어(`segment`/`schedule`)와 길이를 모드별로 지정 |
| `RetentionPolicy.keepEverySegment` | 참이면 움직임 창과 무관하게 닫힌 세그먼트를 모두 `Recordings`로 옮기고 `onPromoted`로 알림. 승격 시점은 `시작 + 길이 + 10초` |
| `LocalMonitoringPipeline.setCaptureMode` | `recording`은 기존 감지·병합, `scheduled`는 감지 없이 keep-all 보관, `live`는 둘 다 없음 |
| `MonitoringHealthReporter` | `schedule-` 접두어도 마지막 녹화로 인식, 슬림 모드 표시 |
| 게이트웨이 `health/status.go` | `captureMode` 허용 값에 `scheduled` 추가. **없으면 녹화 창 동안 상태 전체가 "확인 불가"로 바뀜** |
| 게이트웨이 `recordings/store.go` | `schedule-` 접두어의 시작 시각 해석. 없으면 수정 시각(파일 끝 시각)으로 표시됨 |
| 웹 `app.js` | 녹화 모드 칸에 `켜짐 · 움직임` / `켜짐 · 예약` / `꺼짐` |

### 5.3 왜 보관 관리자를 그대로 쓰는가

용량 제한(`maximumBytes`), 보관 기간, 최소 여유, 보호 파일 제외, 공유 잠금이 모두 `RecordingRetentionManager.enforceRetention`에 있습니다. 연속 녹화용 클래스를 따로 만들면 이 규칙을 복제해야 합니다. 대신 `keepEverySegment` 한 플래그로 "어떤 세그먼트를 남길지"만 바꿨습니다. 움직임 병합(`mergeFinalizedEvents`)은 `segment-` 접두어만 다루므로 `schedule-` 파일에는 손대지 않습니다.

열려 있는 파일을 옮기는 경우: 승격 시점은 파일 이름의 시작 시각 + 길이 + 10초입니다. FFmpeg가 늦게 닫아 아직 쓰는 중이라도 APFS에서 열린 파일의 이름 변경은 쓰기를 끊지 않으며, 파일은 새 위치에서 완성됩니다. 그 몇 초 동안 웹 목록에는 재생되지 않는 파일로 보일 수 있습니다.

## 6. 설정과 스크립트

- 설정 창: `슬림 모드` 체크와 확인 간격(5·10·15·30·60분), `예약 녹화 사용`·요일·시작·종료·파일 길이. 저장하면 앱이 10초 안에 적용합니다.
- `scripts/enable-slim-mode.sh`: sudoers 규칙 설치(관리자 비밀번호 한 번). 설치 뒤 `sudo -n -l`로 규칙이 적용됐는지 스스로 확인합니다.
- `scripts/configure-telegram.sh <토큰>`: 봇 확인(`getMe`), 채팅 번호 찾기, `telegram.json` 저장.
- `scripts/uninstall.sh`: sudoers 규칙과 `MacMonitor` 깨우기 예약을 제거 항목에 추가했습니다. 관리자 비밀번호가 필요하므로 매일 예약 해제와 같은 단계에서 따로 확인받습니다.
- `scripts/diagnose.sh`: `telegram.json` 검증, sudoers 규칙 유무, Energy Saver 잠자기가 "안 함"인지 경고.
- 게이트웨이 `check-config`: `telegram.json`이 있으면 함께 검증합니다.

## 7. Mac에서 확인해야 하는 것 (미확인)

구현했지만 이 환경에서 실행하지 못한 항목입니다. 위에서부터 중요한 순서입니다.

1. **예약 깨우기가 화면을 켜는지.** 켜면 10분마다 잠깐 점등합니다. `pmset -g log | grep -i wake`로 `DarkWake`인지 `Wake`인지 확인합니다.
2. `pmset schedule wake "MM/dd/yy HH:mm:ss" MacMonitor`의 날짜 형식이 받아들여지고 그 시각에 실제로 깨어나는지. 형식과 sudo 규칙은 앱의 시험 예약이 확인하므로, 실패하면 메뉴에 `슬림 모드 대기 — 깨우기 예약 확인 실패`가 보입니다. 실제로 깨어나는지는 기다려서 봅니다.
3. `pmset sleepnow`가 일반 사용자 권한으로 되는지. 안 되면 sudoers 규칙에 추가해야 합니다.
4. 예약 깨우기에서 `didWakeNotification`이 오는지. 오지 않아도 시간 간격 감지로 확인 창이 열리는지 Console 로그로 봅니다.
5. 깨어난 뒤 60초 안에 네트워크가 올라오고 게이트웨이가 텔레그램 메시지를 받는지(Wi‑Fi는 더 느릴 수 있음).
6. LaunchAgent로 실행된 앱에서 `sudo -n`이 규칙을 읽는지.
7. `IOPMSchedulePowerEvent`를 root 없이 부를 수 있는지. 된다면 sudoers 없이 구현할 수 있어 규칙을 없앱니다.
8. 실제 텔레그램 API: long polling, 답장, 409 처리.
9. 10분 세그먼트가 제때 닫히고 `Recordings`로 옮겨진 뒤 Safari에서 재생되는지. 창 종료 시 마지막 짧은 파일도 옮겨지는지.
10. Swift 소스 전체의 컴파일과 새 XCTest.
11. 설정 창 높이가 960pt로 늘었습니다. 21.5인치 iMac(1080pt)에서 메뉴 막대와 Dock을 빼면 거의 꽉 차므로 저장 버튼이 보이는지 확인합니다.
